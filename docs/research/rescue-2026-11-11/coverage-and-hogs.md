## Counting rules supported by the evidence

Observed: `Tessera/Engine/BulkReader.c:101` requests allocated size. The scanner deduplicates hard links by device/inode and zeroes later entries at `FileScanner.swift:608`. That avoids scan-wide double counting, but does not compute exclusive reclaim for a chosen link. A selection can remove the counted link while another link remains outside that selection. This last consequence is an inference from the implementation and hard-link semantics.

Apple documents that [APFS clones share unchanged blocks and volumes share free space](https://developer.apple.com/documentation/foundation/about-apple-file-system). Its [mayShareFileContent property](https://developer.apple.com/documentation/foundation/urlresourcevalues/maysharefilecontent) indicates possible sharing. Therefore allocated size is an observed footprint, not proof of exclusive recoverable blocks. The earlier audit's “allocated size is the right figure for space freed” is too strong.

Design inference for later grilling, not an implementation requirement:

- Keep observed allocated bytes, possible cleanup bytes, and measured capacity change as separate facts. Unknown exclusive recovery must stay unknown.
- Build totals from non-overlapping selected objects. Separate owner backing stores from mounted or exported views. Keep cloud and remote results separate from local capacity.
- Record before and after values for the same filesystem scope and metric. Label important-usage available capacity as such; [Apple defines that API separately from plain available capacity](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumeavailablecapacityforimportantusage). Background writes, purge and shared blocks prevent a simple delta from proving cause.
- Never add snapshots or purgeable space to a capacity value that already includes their availability. Keep Trash moves separate from final removal. Measure after the owner action rather than converting allocated bytes into a promise.

## Evidence limits and next research

This host reports Linux and has no `xcodebuild`. Native Swift/macOS tests and UI captures were not run. Test references above mean assertions inspected in source, not a new passing run. No personal disk was scanned. Every shell read used a finite timeout with TERM then KILL. Only this Markdown file was written; no commit was made.

No evidence here proves which consumer is largest on Ammar's Mac, how often each gap occurs, whether Full Disk Access is needed for each path on the target OS, or whether the current UI misleads users in practice. Those need consented fixtures or device checks and user research. The exact macOS and owner-app versions matter. For example, the older [Parallels reclaim article](https://kb.parallels.com/en/114654) still names a Reclaim button, while [current edition notes mark that control for future removal](https://kb.parallels.com/en/123851). Do not hard-code that old route as a universal handoff.

The local scan goal remains p99 completion within 120 seconds, with continued reading of healthy local drives. No p99 measurement was made. `ci/README.md:23` requires cohort counts, coverage, hardware, OS, workload and cache conditions, and distinguishes synthetic qualification from population proof. Adding detection rules cannot claim performance success from a source-only pass.

Before implementation, grill these unresolved choices: whether largest consumers should lead even when they require owner handoff; whether unrelated coverage gaps should demote a fully inspected candidate; what concrete user task the capacity goal serves; and how to close the gap between reversible Trash review and actual space recovery. These are research questions for the parent task. They are not settled decisions or requests to start implementation.
