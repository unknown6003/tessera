## Cleanup fix

Owned build and fixture trees are removed by iterative postorder traversal.
The walker reopens components from a pinned root descriptor and closes each
parent as it advances. It does not retain one descriptor per depth, change the
working directory, or follow a root or child symlink. The containing path is
resolved once because macOS /tmp is a symlink. The final removal checks the
root's device and inode against the open descriptor.

Each cleanup target is attempted even if an earlier target fails. A cleanup
failure makes the job fail, preserves the original failure and step inventory,
and adds only a target name, error class and errno to the public report. No
private path is included. The report is written after cleanup, so a report
write error cannot skip removal.

The Linux suite passes 68 tool tests. A subprocess sets its descriptor limit
to 32, reproduces the old remover's EMFILE on a 280-level tree, then removes
the same tree with the new walker. It also checks a symlinked containing path
and keeps a linked outside file intact. Other controls reject a symlink root
and a parent-component root. Fault injection checks both an original failed
step and an otherwise successful job: cleanup errors must block both, without
losing the prior steps.

Native cleanup proof and a new full passing campaign remain required. The
heartbeat delay is under separate diagnosis, with profiling kept out of the
qualification data. This recipe change must be reviewed and installed on both
hosts before either lane can qualify a new commit.

## Scheduling diagnosis and policy change

A separate 140-trial diagnostic campaign used the retained 212 Release app.
Two explicit `taskpolicy -b` runs had 33 of 56 trials over 500 ms. Normal
scheduling and Nice 10 alone had zero misses across 84 trials. Counts and
coverage passed throughout. The diagnostic wide folder had 60,000 files;
these trials do not replace the required 100,000-file cohort.

A separate idle Timer control slowed under background policy, but peaked at
254 ms. Activity tokens did not restore its timing. Main-thread samples also
showed SwiftUI layout, view updates and some tree destruction. These results
prove a background-policy contribution, not App Nap or the cause of every
long interval. Host load may amplify the delays. Private evidence:
`/tmp/tessera-perf-diag-00lchyl5/REPORT.md` and `all-trials.csv`.

The LaunchAgent now requests Standard instead of Background, while retaining
Nice 10 and low-priority I/O. SO_CI still prevents activation. The installer is
now part of the signed recipe hash because it sets measurement conditions.
Campaign metadata records the recipe's scheduling policy, and baseline checks
reject a policy change. This field declares the configured policy, not runtime
introspection. Installation must verify the live plist and run qualification
through that installed service, not an explicitly backgrounded diagnostic shell.

Apple documents Standard as the default process type and Background as extra
resource throttling in its [launchd manual](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5).
No heartbeat threshold or scan implementation was changed by this policy fix.
Only a fresh full 400-trial run can qualify it.
